# server/

## 프로토콜을 바꿀 때

- 앱이 새 op나 형식을 쓰기 전에 서버가 지원하는지 `ready` 메시지로 알 수 있어야 한다 (예: `packs: 2`). 예전 서버의 오류 응답에는 `hash` 같은 식별자가 없어서, 앱이 오류를 보고 추측하면 관련 없는 채팅 오류를 잘못 받아들이거나 시간 초과까지 기다린다.
- 예전 클라이언트는 `ready`의 모르는 필드를 무시하므로, 필드를 더하는 것은 하위 호환이다.

## 소켓별 상태

- 크기가 커질 수 있는 소켓별 상태(예: 미완성 업로드 `ws.upload`)는 같은 소켓의 다음 메시지와 `close`만으로 정리하지 않는다. 멈춘 클라이언트도 pong으로 살아 있으므로 heartbeat 루프에서도 오래된 것을 버린다.
- 이런 상한과 시간은 환경변수로 받고 기본값은 운영 값으로 둔다. 테스트는 작은 값으로 서버를 띄워 1초 안에 끝낸다 (`test.js`의 `UPLOADS_MAX`, `UPLOAD_IDLE_MS`, `HEARTBEAT_MS`).

## HTTP 핸들러

- `node:http` 핸들러 안에서 동기로 던진 예외는 잡히지 않고 프로세스를 죽인다. WebSocket까지 함께 끊기므로, 핸들러 안의 DB 호출은 try로 감싸고 503으로 답한다 (`/healthz`, `/metrics`).
- `setInterval` 콜백도 마찬가지다. 주기 작업의 DB 오류는 로그만 남기고 다음 주기에 다시 한다. 시작할 때 한 번 부르는 것은 던져서 바로 죽게 둔다.

## 죽어야 할 때

- 포트를 못 잡는 등 계속 떠 있어도 일을 못 하는 오류는 `process.exit(1)`로 끝낸다. 지표 포트만 살아 있으면 재시작 정책이 동작하지 않는다.
